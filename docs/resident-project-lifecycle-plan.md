## 目标与最小范围

用户随后明确默认在同一自有 IDE／工程中连续读取、修改及必要编译，**不自动保存、不自动关闭**；保存由用户明确决定。用户可以在 IDE 手动修改、保存或关闭，后续请求必须重新读取内存和磁盘状态，不回滚或覆盖。只有明确要求或专项持久化验收才关闭重开；退出只用于明确收尾或维护。该目标尚未实现，历史保存重开和可信退出验收仍属于原版本。

先做一个可验证的纵向流程：同一个 MCP 服务启动并持有一个已核实的 IDE 实例，在同一个指定工程句柄中串行完成“读 → 一个已有的限定源码编辑动作 → 再读”，验证磁盘不变、内存修改可读；按需编译及用户明确要求的保存分别验证。首批工具须逐项列明，现有自动保存工具未经适配不得用于新模式，不宣称38项工具已切换。只处理服务自有实例，不接管已有用户 IDE，不增加 GUI、聊天客户端、守护框架或隔离专项。其他工程切换、跨客户端重接、服务退出后保留均独立待验。

## 当前实现为何会关闭与退出

| 层次／入口 | 源码中已确认的行为 | 新模式需要处理的依赖 |
|---|---|---|
| [adapter](../src/adapter.ts) `executeObserved` | 每次请求生成 launchId、发布 request.json，然后 spawn IDE，以固定 `--profile`、`--runscript` 和请求路径启动；当前没有常驻多请求循环 | IDE启动身份与每条请求身份要分开；同实例串行请求各有独立请求指纹、派发和结果 |
| 同文件 `published`／`reconcile` | 等待进程退出并发布退出证据，再核对结果、正常关闭回执和退出后文件哈希 | 不能只去掉等待；应有独立的请求完成凭据、句柄与保存版本核对，继续观察进程异常 |
| [worker](../bridge/worker.py) `dispatch` | 默认要求 `projects.primary` 为空；打开指定文件；`finally` 调用 `lifecycle_close(..., "final-cleanup")` | 自有句柄复用与外部句柄拒绝须分开；每条请求不能再把自有已开工程判成未授权占用 |
| 同文件 `lifecycle_save_reopen` | `project.save()` → `owned.close()` → `projects.open(..., primary=True)` | 默认保存应保留句柄；只有显式重开模式走原关闭／重开逻辑，分别报告证据 |
| 同文件主入口及 [native_exit](../bridge/native_exit.py) | 主线程执行前要求空工程并预检正常退出能力；结果发布后 `closer.queue()` 排队公开 FileExit | 例行请求不再以空工程或退出能力作为完成条件；不因此取消正常退出、崩溃和缺证的观察 |
| [service](../src/service.ts) 结果校验 | 多处要求 `reopened===true`，并核对重开原文、任务／绑定和保存哈希 | 按工具明确“同句柄读回”“已保存”“已重开”三种事实；不能缺少重开却填true |
| [server](../src/server.ts)、[ServiceLifecycle](../src/service-lifecycle.ts) | stdin EOF／信号触发停止受理、排空队列、等待退出观察、条件释放租约和关闭transport | 当前关闭服务流程仍与子进程退出绑定；客户端EOF不能被设计成隐式关闭工程或杀IDE |

写工具内的关闭重开不是只有末尾一处。静态已查范围如下，**是迁移清单，不是新模式支持表**：

- `task_config_update`、`task_create`、`task_call_append`、`task_call_replace`：即时读回、保存重开及服务层任务／PROGRAM保全相互依赖。
- `variable_edit`／`code_apply_change`、POU／DUT／Method／Property创建：源码、原生身份和部分专用证据包含 `reopened` 阶段。
- [organization](../bridge/organization.py) 的文件夹创建／对象移动，以及 [library_reference](../bridge/library_reference.py) 的引用新增／占位符解析、[library_placeholder_clear](../bridge/library_placeholder_clear.py)：内部保存重开后校验清单。
- [project_create](../bridge/project_create.py) 原生新建也包含保存、关闭、重开及最终清理；`project_save` 明确承诺保存关闭重开，并由服务层验证。
- 只读路径的 `afterCloseDiskHash` 与 adapter 的 `postExitDiskHashObserved` 具有明确阶段含义，不能在保持打开时沿用名称伪造该阶段。
- [contracts](../src/contracts.ts) 中 `library_placeholder_clear`、三个任务写工具及新建证据等含 `reopened: literal(true)`；其余工具即使Schema仅为可选boolean，也有服务校验、说明或实际行为承诺。需逐项审计输入输出、错误语义、版本与初始化说明，不能只删FileExit便宣称契约语义兼容。

## 最小实施步骤与完成判据

1. **固定入口和单实例所有权。** 复用现有原生脚本及固定结构化请求，不执行用户文本。启动证据绑定可执行文件、脚本指纹、PID与创建身份；工程绑定实际路径、原生身份和句柄代次。会话只持有一个自有工程，不靠PID、名称或锁文件存在推定所有权。
2. **串行请求与主线程。** 在当前服务存活范围内验证固定接收入口；I/O接收不占用主线程等待，工程调用只经公开主线程入口。每条请求有独立operationId、requestId和指纹，一次只派发一个；running查询原操作，重复请求返回原结果。先取得两次只读请求均由同一实例、同一句柄完成的证据。无法确认入口生命周期就停止相关实施，不退回私有处理器。
3. **请求完成与进程寿命分开。** 结果绑定原请求、进程创建身份、句柄代次、实际目标和内存／磁盘版本，并有必要原生读回。编辑保留检查点、写前复查、写后授权差异和首错，默认不保存或关闭。按需编译绑定实际内存版本；用户明确要求的保存另外取得save返回、同句柄读回和磁盘哈希。未保存编译不能宣称对应磁盘文件。缺结果、进程丢失、外部变化、超时或部分写入不确定时停止，不盲重放、不回滚或恢复性保存。
4. **逐工具迁移。** 首批限定内存读／改／再读，按需编译及显式保存分别接入。现有自动保存／重开工具未经适配必须拒绝新模式，不能暗中退回旧模式或假报未保存。未重开不返回reopened=true，独立重开证据不与同句柄读回混同。Schema、版本、服务独立校验及初始化规则随未来实现统一评审，本轮全部不改。
5. **最小验收。** 同服务、同PID及创建身份、同工程句柄连续读／改／再读；只有授权源码变化，其他受检身份、任务和源码保全，磁盘不变且内存修改可读。按需编译与用户明确要求的保存各自验证版本对应。用户手动修改、保存或关闭后，下一请求重读实际状态，原句柄失效或有冲突即停止，不覆盖用户操作。默认完成后工程仍打开，无save／close／FileExit。另用离线故障用例验证缺证不会继续写入。真实重开和正常退出只在单独明确要求时验证。

进程异常监测仍需贯穿服务会话：进行中请求遇到崩溃须按不确定规则处理；已经有完整保存证据的先前结果与之后的进程故障分别记录，不批量改写历史终态。没有可核对的证据时不伪造成功或退出码。
