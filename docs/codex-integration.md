# Codex 本机接入（0.14.0 固定构建）

本说明使用现有二十项工具，不改变工程服务、桥接、Schema、工作指令或隔离机制。0.15.0 开发工作区另行保留；不要让接入配置引用正在变化的其他分支构建。此处路径均为示例，不能直接视作另一台电脑的真实登记。

main现提供0.15.0候选版；本文所述Codex接入验收、模板路径示例及已配置的独立固定构建仍为0.14.0。本次main合并不改变该入口或私有配置，不证明Codex已加载、收到新Schema或验收0.15.0；需要升级时另按正常服务移交和实际加载核对办理。

## Windows 环境与固定构建

需要 Windows Node 22 或以上、InoProShop 1.9.1.6 和可用的 Codex 客户端认证。使用 Windows 可执行文件和绝对路径；WSL 客户端、Linux 路径和跨宿主启动本轮不适用。`codex mcp-server` 是把 Codex 作为服务端，不是接入本工程服务的命令。

先核对 `codex --version`、`codex --help`、`codex exec --help` 及 `codex mcp --help`。桌面包版本与 PATH 中 CLI 的版本可能不同，不能互相替代。

在独立且固定的检出中执行 `npm ci`、`npm run build`。服务入口为该检出的 `dist/server.js`，Node、入口和 `cwd` 必须对应同一 Windows 构建。该检出需要持续保留；不能在配置仍指向它时删除工作区。

## 配置与加载

备份将修改的配置。参考 [模板](../config/codex.example.toml)，填写实际已登记的 `INOPRO_DATA_DIR`、IDE 可执行文件、Profile 及固定检出路径。不要复制私人账号配置、认证文件或其他 MCP 服务设置。不要为了连接成功改到空数据目录，也不要沿用 fixture 模式。

官方支持在受信任项目的 `.codex/config.toml` 中配置 MCP。项目的信任记录位于用户配置 `projects.<path>.trust_level`；只登记已核对的独立检出，保留权限检查。本模板选用 `on-request` 与 `read-only`，不使用跳过权限或沙箱的开关。只读 MCP 是服务进程执行的能力，不能把终端只读沙箱当成工程写入授权或服务端权限边界。

本机接入使用项目配置，避免把新服务加到所有正在运行的桌面会话。`codex -C <固定检出> mcp list --json` 可以核对配置是否被识别，但不证明服务已连接，更不证明模型收到全部指令。CLI 新进程读取配置；已有桌面会话是否重新加载需由实际连接证据确认。不能仅因文件写入成功便报告当前桌面已经加载。

三个超时分别设置：`startup_timeout_sec=30` 是初始化等待；`tool_timeout_sec=180` 是客户端等待；`INOPRO_TIMEOUT_MS=120000` 是 IDE 子进程上限，`INOPRO_RESPONSE_WAIT_MS=15000` 控制服务初次响应等待。客户端收到 running 后查询原操作，不能重放。DSH 的 `maxInstructionBytes` 不属于 Codex，不能放进本模板。

配置字段依据 [OpenAI 官方 MCP 文档](https://developers.openai.com/codex/mcp) 与 [配置参考](https://developers.openai.com/codex/config-reference)，仍应以本机帮助及实际加载结果核对。不要将更高版本文档的新字段无条件套用到旧客户端。

## 一次只交给一个客户端

Codex 桌面、独立 CLI 和 DSH 可能各自启动 stdio 子进程。共享配置不等于共享一个服务进程；本项目没有多客户端并行工程支持。

移交前先查询或只读核对现有服务租约、操作记录及隔离登记，确认没有正在执行或未确认停止的任务。历史受控隔离工程的 unknown 仍然未知，不能当成当前任务，也不能绕过隔离。确认原客户端空闲、输入框为空后，正常退出或停用对应 MCP，等待其服务进程实际退出。不能确认时停止移交，不强杀、不删锁、不清空记录。

新客户端继续使用原数据目录，让既有租约核对机制正常处理已退出所有者。若报占用、冲突或冻结，保留原请求和证据，不能手工接管。归还 DSH 时先结束 Codex 的 MCP 会话并确认服务退出，再正常启动 DSH；不能让两个客户端同时争用。

模型必须实际调用 MCP；终端直接读取工程、手工 JSON-RPC 和把旧结果交给模型都不能替代验收。独立初始化只用来核对服务版本、二十工具、Schema 和实际 instructions，不派发工程操作。完整工程哈希和 `.opt` 等附属文件分开比较。

## 故障与证据

- CLI 启动前的路径或参数错误、模型请求失败和工程操作失败分别归档。没有模型/工具记录时不能写成工程已执行。
- 账号可用模型与桌面默认模型可能不同。使用本机已安装版本支持的 `codex debug models` 核对实际目录，再仅为所需工作区选择模型；不要猜测别名、改动全局账号或把模型拒绝归咎工程服务。
- 非交互 `exec` 实测记录的审批策略为 `never`（不弹审批），只读沙箱仍生效；配置中的 `on-request` 不是其会弹交互审批的保证。本轮没有开启绕过开关。需要审批的后续工作不能据此视为已获放行。
- `mcp list` 只证明配置；服务初始化响应证明发送；客户端协议记录及实际模型工具调用分别证明可观测接收和使用。完整指令是否进入模型上下文，观察不到就标未知。
- `codex debug prompt-input` 的输出可能只含静态输入，不能把它当作当前 MCP 已加载的证明。不要收集完整凭据、其他聊天或完整模型请求日志。
- 本机 Windows Node 的 `NODE_OPTIONS --require` 若用于局部被动取证，应使用正确转义的路径。取证只复制工程服务协议，不过滤或替换返回，不属于产品运行要求；结束后不写入长期配置。
- 结果未知时按 [入门说明](getting-started.md) 保全原操作，停止写入；本轮不恢复隔离工程或修改执行策略。

实际验收结果、原始答复、首次失败和客户端最终状态见本轮本地复核 ZIP，不能用本文的任务示例充当已执行证据。Codex 的修改、编译、保存关闭重开及最终比较闭环需另行验证；不从只读接入推定写入、桌面交互、链接点击或运行已通过。原 unknown、历史 11/12 质量、CmpLog 和脚本信任限制不变。
