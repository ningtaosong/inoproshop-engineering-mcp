# 登记前直接打开的维护隔离（0.27.1 修复候选）

本修复仅处理 `project_open` 已持久化暂定直接工程身份、已派发 IDE，但在正式登记前变为 `unknown` 的情况。它使维护评估能识别待隔离文件，**不判定原操作成功或失败**。没有新增 MCP 工具；30 项工具及输入 Schema 保持，S5b 占位符功能不在本分支。

## 归属与证据

旧的已登记工程及 `project_open_copy` 仍使用原登记归属和 v1 计划。登记前的直接打开使用 v2 计划，明确标记 `ownershipBasis=provisional-direct`；原暂定工程身份不写成正式登记。原隔离账本和独立锚点的 envelope 格式不迁移，v1 已提交记录继续可读。

只有以下证据能联合确认时，才允许产生 eligible 的 v2 计划：带校验的原操作、请求指纹和 requestId、暂定工程及会话身份、直接模式路径、受理时登记版本、当前真实文件身份与派发前磁盘哈希、原 IPC 请求的直接文件保护字段及派发标记、同一原进程实例的服务租约和来源锁。原操作未记录派发时的文件 ID，因此不能宣称已核对历史文件 ID；原服务、桥接和原生占用标记的进程状态必须分别核对，PID 当前退出不能推断 IDE 操作的结果。注册冲突、硬链接等文件别名、其他未决操作、损坏或不完整记录均阻止计划。

只读 `evaluate`／`plan` 不取得工程租约或更改现场。真正 `commit` 仍需单独显式操作，取得维护排他标记和文件读锁后重新评估全部证据；计划、锁、文件或进程变化即拒绝。提交中断继续全局冻结，重复提交按原计划 ID 去重。已提交 v2 隔离以暂定 projectId、路径、realpath 和文件身份别名拦截打开、导入及工程操作；原操作保持原始状态，可信迟到结果或同身份登记也不自动解除隔离。只有所有其他未决操作已有有效处置，无关工程才可恢复派发。

完整的原工程终态、工程内容、设备及任务配置、适用编译证据仍缺失；隔离不是恢复、回滚或运行验收。
